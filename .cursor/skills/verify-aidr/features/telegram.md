# Telegram workflow

The public Telegram channel is the third delivery path beside the Chrome extension and email digest. Public-link validation is credential-free; sending a real message requires explicit bot configuration.

## Sub-features

- `telegram-link` exposes the public channel from the header, phone menu, footer, and `/subscribe`.
- `telegram-utm` adds `utm_source=telegram` to digest and story links generated by the Worker.
- `telegram-delivery` formats daily digest and trending-story messages and records send outcomes.

## How to get to it (user POV)

- Open `https://aidr.today/subscribe` and choose Telegram.
- Open the public channel from the header or footer.
- Read a digest message and follow its Read/Discuss links back to AI;DR.

## Driving it with verify-aidr

Preconditions:

- `verify-aidr doctor` reports `ok: true`.
- Do not read, print, or mutate Telegram credentials for this read-only check.

- **Public link proof.** Run `.cursor/skills/verify-aidr/bin/verify-aidr drive telegram`. HTTP 200 HTML must contain `Telegram` and `t.me/aihomnay`; the report must say delivery was not run because it is credential-gated.
- **Existing guide proof.** Run `.cursor/skills/verify-aidr/bin/verify-aidr drive extension` to verify `/subscribe` and the `/extension` redirect.
- **Formatter and adapter tests.** Run `pnpm --filter @aidr/web exec vitest run worker/__tests__/notify.test.ts`.
- **Campaign proof.** Run `.cursor/skills/verify-aidr/bin/verify-aidr drive analytics` and confirm the Telegram campaign landing and channel-link checks pass.

## Gotchas

- Never put `TELEGRAM_BOT_TOKEN` or `TELEGRAM_CHAT_ID` in evidence, command output, or the skill.
- A public channel link is not proof that a message was delivered; delivery requires an explicitly configured Worker environment.
- Telegram has no reliable read receipts, so generated links use UTM attribution instead.
